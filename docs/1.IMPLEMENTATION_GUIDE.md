## Introduction

This guide documents a production-ready approach to handling dates, times, and timezones in a web application. The goal is to ensure that events created in one timezone are accurately displayed in any other timezone, without data loss or confusion.

### The Problem

When building applications that deal with events across timezones, common issues include:

- **Date Loss**: Dates shifting by a day when converting between timezones
- **DST Confusion**: Daylight Saving Time causing unpredictable time shifts
- **Display Inconsistencies**: Same event showing different times for different users
- **Data Integrity**: Storing ambiguous date information that can't be reliably converted

### The Solution

**Store in UTC, Display in Local**

This simple principle solves most timezone-related issues:
1. **Backend**: Always store dates as UTC (ISO 8601 format)
2. **Frontend**: Convert UTC to user's local timezone for display
3. **Input**: Convert user's local input to UTC before sending to backend

## Core Principles

### 1. Single Source of Truth

**Always store dates in UTC**

```typescript
// ✅ GOOD: Stored in database
{
  "startDateTime": "2025-01-15T04:30:00.000Z",  // UTC
  "timezone": "Asia/Kolkata"  // Original timezone for reference
}

// ❌ BAD: Storing local time without timezone
{
  "startDateTime": "2025-01-15T10:00:00",  // Which timezone?
}
```

### 2. ISO 8601 Format

Always use ISO 8601 for date strings:

```typescript
// ✅ GOOD
"2025-01-15T04:30:00.000Z"  // ISO 8601 with UTC indicator

// ❌ BAD
"01/15/2025 10:00 AM"  // Ambiguous format
"2025-01-15 10:00"      // No timezone information
```

### 3. Never Trust Client Time

The client's system clock might be wrong. Always:
- Store server-generated timestamps for `createdAt`, `updatedAt`
- Use user's timezone only for display conversion
- Validate date ranges on the server

### 4. Preserve Original Timezone

Store the original timezone for reference:
- Helps with debugging
- Useful for displaying "Created in Asia/Kolkata"
- Allows reconstructing the original local time if needed

## Frontend Responsibilities

### 1. Timezone Detection

```typescript
// src/utils/timezone.ts
export const getUserTimezone = (): string => {
  try {
    return Intl.DateTimeFormat().resolvedOptions().timeZone;
  } catch (error) {
    return "UTC"; // Fallback
  }
};
```

**Why**: The browser's `Intl` API provides the most reliable timezone detection.

### 2. Input Handling

When using `<input type="datetime-local">`:

```typescript
// User sees and inputs in their local timezone
<input 
  type="datetime-local" 
  value="2025-01-15T10:00"  // Displays in user's local time
/>

// When submitting, attach timezone
const payload = {
  startDateTime: formData.startDateTime,  // "2025-01-15T10:00"
  timezone: getUserTimezone(),  // "Asia/Kolkata"
};
```

**Important**: The `datetime-local` input:
- Shows time in user's browser timezone
- Returns a string in format `YYYY-MM-DDTHH:mm`
- Does NOT include timezone information
- That's why we must attach the timezone separately

### 3. Display Conversion

```typescript
// Convert UTC to user's timezone for display
import { formatInTimeZone } from "date-fns-tz";

const displayTime = formatInTimeZone(
  utcDateString,
  userTimezone,
  "PPP 'at' p"  // "Jan 15, 2025 at 10:00 AM"
);
```

### 4. Edit Form Population

When editing, convert UTC back to local time for the input:

```typescript
import { format } from "date-fns";
import { toZonedTime } from "date-fns-tz";

// Convert UTC to local time for input
const localDate = toZonedTime(utcDateString, userTimezone);
const inputValue = format(localDate, "yyyy-MM-dd'T'HH:mm");

<input 
  type="datetime-local" 
  value={inputValue}  // Correctly shows in user's timezone
/>
```

## Backend Responsibilities

### 1. Receive with Timezone

Accept both the datetime and timezone from the client:

```typescript
// API receives
{
  "startDateTime": "2025-01-15T10:00",  // Local time
  "timezone": "Asia/Kolkata"  // User's timezone
}
```

### 2. Convert to UTC

```typescript
import { fromZonedTime } from "date-fns-tz";

// Convert local time to UTC
const localDate = new Date(body.startDateTime);
const utcDate = fromZonedTime(localDate, body.timezone);
const utcString = utcDate.toISOString();  // "2025-01-15T04:30:00.000Z"
```

### 3. Validate

```typescript
// Validate date range
if (startDateUTC >= endDateUTC) {
  return error("End date must be after start date");
}

// Validate timezone
try {
  Intl.DateTimeFormat(undefined, { timeZone: timezone });
} catch {
  return error("Invalid timezone");
}
```

### 4. Store in UTC

```typescript
// Database entry
{
  "id": "uuid",
  "startDateTime": "2025-01-15T04:30:00.000Z",  // UTC
  "endDateTime": "2025-01-15T06:30:00.000Z",    // UTC
  "timezone": "Asia/Kolkata",  // Original timezone
  "createdAt": "2025-01-10T12:00:00.000Z"  // Server timestamp
}
```

### 5. Return UTC

When sending data to frontend, return UTC strings as-is:

```typescript
// API response
{
  "success": true,
  "data": {
    "id": "uuid",
    "startDateTime": "2025-01-15T04:30:00.000Z",  // UTC
    // ... other fields
  }
}
```

The frontend will handle conversion to user's timezone.

## Common Pitfalls & Solutions

### 1. Date Shifting by One Day

**Problem**: User selects "Jan 15" but it saves as "Jan 14" or "Jan 16"

**Cause**: Incorrect timezone conversion

**Solution**:
```typescript
// ❌ WRONG: Creates date in UTC, not local
const date = new Date("2025-01-15T10:00");  // Interpreted as UTC

// ✅ RIGHT: Create date in user's timezone, then convert to UTC
const localDate = new Date("2025-01-15T10:00");
const utcDate = fromZonedTime(localDate, userTimezone);
```

### 2. DST (Daylight Saving Time) Issues

**Problem**: Events shift by an hour during DST transitions

**Cause**: Using fixed UTC offsets instead of IANA timezones

**Solution**:
```typescript
// ❌ WRONG: Fixed offset
timezone: "UTC+5:30"  // Doesn't handle DST

// ✅ RIGHT: IANA timezone
timezone: "America/New_York"  // Automatically handles DST
```

### 3. Midnight Edge Cases

**Problem**: Event at midnight shows as previous day

**Cause**: Timezone conversion pushing time to previous day

**Example**:
- User in India creates event: Jan 15, 12:00 AM IST
- Converts to UTC: Jan 14, 6:30 PM UTC (previous day!)
- User in Japan sees: Jan 15, 3:30 AM JST (correct day)

**Solution**: This is actually correct behavior! The UTC date is accurate. Display logic must convert properly.

```typescript
// Always convert UTC to user's timezone for display
const displayDate = formatInTimeZone(
  utcString,
  userTimezone,
  "PPP"  // "Jan 15, 2025"
);
```

### 4. Invalid Timezone Names

**Problem**: Timezone like "PST" or "IST" causes errors

**Cause**: Using abbreviations instead of IANA names

**Solution**:
```typescript
// ❌ WRONG: Abbreviations
"PST", "EST", "IST"

// ✅ RIGHT: IANA timezone identifiers
"America/Los_Angeles", "America/New_York", "Asia/Kolkata"
```

### 5. Comparing Dates from Different Timezones

**Problem**: Comparing local dates directly

**Solution**: Always convert to UTC first:

```typescript
// ❌ WRONG
const date1 = new Date("2025-01-15T10:00");  // Ambiguous
const date2 = new Date("2025-01-15T15:00");  // Ambiguous
date1 < date2  // Unreliable

// ✅ RIGHT
const utc1 = convertToUTC("2025-01-15T10:00", "Asia/Kolkata");
const utc2 = convertToUTC("2025-01-15T15:00", "America/New_York");
new Date(utc1) < new Date(utc2)  // Reliable
```

### 6. Server Time vs. User Time

**Problem**: Using server's local time for timestamps

**Solution**: Always use UTC on the server:

```typescript
// ❌ WRONG
createdAt: new Date().toLocaleString()  // Server's local time

// ✅ RIGHT
createdAt: new Date().toISOString()  // UTC
```

## Reusable Patterns

### Pattern 1: Timezone Hook

Copy `useTimezone.ts` to any project:

```typescript
// In your new project
import { useTimezone } from "@/hooks/useTimezone";

function Component() {
  const { timezone, isLoading } = useTimezone();
  
  if (isLoading) return <Loading />;
  
  return <div>Your timezone: {timezone}</div>;
}
```

### Pattern 2: Date Converter Hook

Copy `useDateTimeConverter.ts` for easy conversions:

```typescript
import { useDateTimeConverter } from "@/hooks/useDateTimeConverter";

function Component({ utcDate, userTimezone }) {
  const { formatDateTime } = useDateTimeConverter();
  
  return (
    <div>
      {formatDateTime(utcDate, userTimezone, "PPP p")}
    </div>
  );
}
```

### Pattern 3: Utility Functions

All functions in `src/utils/timezone.ts` are pure and portable:

```typescript
// Copy the entire file to your project
import {
  getUserTimezone,
  convertToUTC,
  formatEventDateTime
} from "@/utils/timezone";

// Use anywhere
const tz = getUserTimezone();
const utc = convertToUTC(localDate, tz);
const display = formatEventDateTime(utc, tz);
```

### Pattern 4: Form Pattern

The datetime-local pattern works for any form:

```typescript
// 1. User inputs in local time
<input type="datetime-local" value={localTime} />

// 2. On submit, attach timezone
const payload = {
  dateTime: formData.dateTime,
  timezone: getUserTimezone(),
};

// 3. Backend converts to UTC
const utc = convertToUTC(payload.dateTime, payload.timezone);

// 4. Store UTC in database
await db.save({ dateTime: utc });
```

## Testing Considerations

### 1. Test Across Timezones

Manually test by changing browser timezone:

**Chrome DevTools**:
1. Open DevTools → Settings (⚙️)
2. More Tools → Sensors
3. Location → Select timezone
4. Reload page

**Firefox**:
1. Type `about:config` in address bar
2. Search `intl.tz.override`
3. Set to IANA timezone (e.g., "America/New_York")
4. Reload page

### 2. Test DST Transitions

Test dates around DST changes:
- March (Spring forward)
- November (Fall back)

### 3. Test Edge Cases

- Midnight events
- Events spanning DST transition
- Multi-day events
- Past events
- Far future events

### 4. Test Validation

- Start date after end date
- Invalid timezone strings
- Empty fields
- Very long titles/descriptions

### 5. Unit Test Utilities

```typescript
// Example tests for timezone.ts
describe("convertToUTC", () => {
  it("converts India time to UTC", () => {
    const result = convertToUTC(
      "2025-01-15T10:00",
      "Asia/Kolkata"
    );
    expect(result).toBe("2025-01-15T04:30:00.000Z");
  });
  
  it("converts LA time to UTC", () => {
    const result = convertToUTC(
      "2025-01-15T10:00",
      "America/Los_Angeles"
    );
    // LA is UTC-8 in winter
    expect(result).toBe("2025-01-15T18:00:00.000Z");
  });
});
```

## Conclusion

Handling timezones correctly requires discipline but the pattern is straightforward:

1. **Store in UTC** - Single source of truth
2. **Display in Local** - Convert for the user
3. **Validate Everywhere** - Never trust input
4. **Test Thoroughly** - Especially edge cases

By following this guide, you can build timezone-aware applications that work reliably for users around the world.
